## 1. The twelve things that block open beta

Eleven confirmed P0s plus the critic's P0. Grouped by root cause, because several share one.

**A. Identity is forgeable.** Telegram Mini App rows store `device_id = "tg:<telegram_id>"`
(`auth.ts:176`), and the device-id branch resolves that column on a length check alone. A Telegram user id
is public. One header — `x-device-id: tg:<id>` — returns the victim's account and mints them a 24h session
token. If the victim has not verified email, `POST /auth/register` then takes the row permanently.

**B. Rate limiting is structurally void, three independent ways.** `trustProxy: true` makes `req.ip`
attacker-supplied, so every IP-keyed limit is a no-op. Account creation happens in the auth `preHandler`,
which Fastify runs *before* route rate limits — so unauthenticated callers insert unbounded `users` +
`companion_state` rows, and **even refused requests create a row first**. `/auth/register` is keyed per
freshly-minted `userId`, so the limit resets with every new account. Together these void the per-user LLM
budgets too: the budget is per-account and accounts are free and infinite.

**C. Real lost-pet data can be corrupted by any user.** `POST /sightings` accepts out-of-range lat/lng and
permanently overwrites a pet's last-seen coordinate; any caller can move a real pet's pin repeatedly and
overwrite `placement_source` with the highest-authority value. Given that this table holds reports from
people who walked real streets looking for real animals, this is the one I would fix first.

**D. Location privacy is broken in both directions.** Territory marks publish other users' **un-jittered**
GPS track points city-wide to any logged-in caller. And the presence jitter is *exactly invertible* from
data in the same response, so `/presence` yields every active walker's true live position.

**E. New Telegram signups are already broken.** `onConflictDoNothing({ target: users.telegramId })` cannot
work: migration `0010` builds a **partial** unique index (`WHERE telegram_id IS NOT NULL`) and Postgres
will not infer one for `ON CONFLICT`. It raises `42P10`. Latent in a closed invite-gated beta because no
new signups arrive — it detonates on the day you open.

**F. One slow query wedges the whole API, invisibly.** No `statement_timeout` anywhere. A running query
holds a pool connection indefinitely; `max` is 10. Ten slow queries and the API is dead — while `/health`,
which never touches the database, keeps returning 200, so Fly never restarts it.

### 1. [P0] Any Telegram user's account can be taken over by sending `x-device-id: tg:<telegram_id>` — no signature, no invite, no door

- **Where:** `server/src/auth.ts:76` · **Category:** `auth-bypass`

**Evidence.** Read server/src/auth.ts in full. Mini App accounts are stored with `users.device_id = 'tg:' + telegram_id` (auth.ts:176, restated in the schema comment at server/src/db/schema.ts:19-22 and in wipe-users.ts:130). `device_id` is a plain NOT NULL UNIQUE column (server/src/db/schema.ts:25). The device-id branch of the preHandler looks a row up by exactly that column with no check on the shape of the value beyond 8..128 characters, and `resolveByDeviceId` returns any existing row unconditionally (auth.ts:78-84, comment included). `resolved()` (auth.ts:40-42) sets `registered: doorFor(row) === 'open'`, so a registered+verified victim's row makes `passDoor` (auth.ts:234-239) return immediately. I confirmed via grep across server/src/routes and server/src/services that nothing else re-checks `authVia`, so a `via:'device'` identity is treated identically to a Telegram-signed one everywhere.

**Exploit / failure path.** Attacker learns a victim's Telegram user id (not a secret: it is visible to every bot the person uses, in forwarded-message metadata, and via any of the public "what is my id" bots; this app itself is a Telegram bot ecosystem that crossposts to public lost-pet groups). Attacker sends `curl -H 'x-device-id: tg:123456789' https://<api>/auth/me`. The SELECT on users.device_id matches the victim's row, req.userId becomes the victim's id, the response body is the victim's account (masked e-mail, nickname, pet, telegram flag), and the response header `x-session-token` hands the attacker a 24-hour session slip minted for the victim (auth.ts:359). From there every authenticated route in the app answers as the victim: their tokens, territory, companion chat, presence, /auth/profile, /auth/avatar spend. If the victim is registered but not yet e-mail-verified, POST /auth/register with the attacker's own e-mail and password succeeds — routes/auth.ts:290 only refuses when BOTH registeredAt and emailVerifiedAt are set — converting the hijack into a permanent credentialed takeover of the victim's row. The id space is also enumerable: existing ids answer with a populated account, absent ids mint a fresh one, so the two are distinguishable from the /auth/me body.

**Impact.** Pre-authentication account takeover of every Telegram Mini App user, from a single header, with no rate limit that matters (see the trustProxy and account-flood findings). This invalidates the prior audit's note that "The Telegram path is properly signed and fine" and that device ids are "client-generated random hex (not enumerable)" — for Telegram users the device id IS a public identifier.

**Fix.** Make the synthetic Telegram id un-addressable through the device-id header. In auth.ts:350, reject any presented `x-device-id` matching /^tg:/i before calling resolveByDeviceId (401), and add a check fixture asserting it. Better still, stop overloading `device_id` as the Telegram key: give Telegram rows an opaque random device_id (e.g. `nanoid()`) and rely on the existing `telegram_id` column for identity, so no public value is ever a credential.

### 2. [P0] `trustProxy: true` makes `req.ip` attacker-supplied, so every credential rate limit is a no-op — unlimited password guessing and a trivial scrypt memory-exhaustion DoS on the 512MB machine

- **Where:** `server/src/index.ts:93` · **Category:** `rate-limit-bypass`

**Evidence.** Read server/src/index.ts:60-147 and server/src/lib/rateLimit.ts in full. `trustProxy: true` in Fastify is passed to proxy-addr as a trust-everything predicate, so `req.ip` resolves to the left-most (furthest, i.e. client-supplied) entry of X-Forwarded-For rather than the hop Fly appended. `limitAuth` is the only limiter on /auth/login, /auth/forgot, /auth/reset, /auth/refresh, /auth/verify and /auth/logout (routes/auth.ts:461, 482, 508, 607, 618, 632), and it keys solely on that value. Cost of one /auth/login: server/src/lib/password.ts:56-63 sets N = 1<<15, R = 8, MAXMEM = 128*N*R*2, and verifyPassword (password.ts:128-137) spends a full derivation even for an unknown address (password.ts:130-132) — 128*32768*8 = 33.5 MB of scrypt working memory and, per the file's own comment at password.ts:42, "tens of milliseconds" on this VM. fly.toml/the brief put this on one shared-cpu-1x with 512 MB.

**Exploit / failure path.** `for i in $(seq 1 100000); do curl -s -H "X-Forwarded-For: 10.$((RANDOM%255)).$((RANDOM%255)).$((RANDOM%255))" -H 'content-type: application/json' -d '{"email":"victim@gmail.com","password":"guess'$i'"}' https://<api>/auth/login; done` — every request lands in a fresh rate-limit bucket, so the 10/min ceiling never fires and the password of any known address can be guessed without limit. Run ~15 of those concurrently instead of serially and each in-flight request holds ~33 MB of scrypt state: the Node process on a 512 MB machine is OOM-killed, taking the whole API down for every real user mid-walk. No credentials and no account are needed for either.

**Impact.** Brute-force protection on every credential endpoint is decorative, and an unauthenticated attacker can knock the single production machine over at essentially zero cost — exactly the 'falls over under beta load' case, except deliberate.

**Fix.** Set `trustProxy: 1` (trust only the one hop Fly appends) instead of `true`, so req.ip is the address Fly observed and cannot be chosen by the caller. Independently, bound concurrent scrypt work: a small semaphore (e.g. 2-4 in-flight derivations, queue the rest) around hashPassword/verifyPassword so memory use is capped regardless of request rate, and add a per-address (not per-IP) failure counter on /auth/login.

> **Verifier correction.** The brute-force half is correct as written. The DoS half is right in conclusion but wrong in mechanism, and should be restated before it goes in the report.

### 3. [P0] Every new Telegram Mini App signup 500s: `ON CONFLICT ("telegram_id")` cannot infer the partial unique index

- **Where:** `server/src/auth.ts:191` · **Category:** `broken-signup`

**Evidence.** Read auth.ts:141-208, server/src/db/schema.ts:23-35 (telegramId is declared with no .unique(), so drizzle creates no constraint of its own), and every migration that mentions telegram_id — grep over server/migrations/*.sql returns only 0010_telegram_auth.sql (the partial index above) and a comment in 0032_invite_codes.sql. I then read the drizzle SQL builder at node_modules/drizzle-orm/pg-core/query-builders/insert.js:104-113: with a `target` and no `where`, it emits `sql`(${targetColumn})${whereSql} do nothing`` where whereSql is undefined — i.e. `on conflict ("telegram_id") do nothing`, with no index_predicate. The sibling device-id insert at auth.ts:107-111 targets `users.deviceId`, which IS a plain UNIQUE column (schema.ts:25), so that path is unaffected — only the Telegram path is. LIMIT: this is a read-only audit with no database, so I could not execute the statement; the conclusion rests on the emitted SQL, the migration text and Postgres's documented inference rule.

**Exploit / failure path.** A new user opens the Mini App. validateInitData passes, resolveByTelegram finds no row with that telegram_id (auth.ts:146-150), and the INSERT at auth.ts:180 runs. Postgres rejects the statement with 42P10. That error is neither InviteRequiredError nor RegistrationRequiredError, so auth.ts:339 rethrows it, the preHandler fails, and index.ts's error handler masks it as a 500. The person sees a broken first screen and can never create an account; retrying produces the same 500 forever. Existing Telegram users are unaffected (they return at auth.ts:151), which is exactly why this would survive testing on the owner's own account.

**Impact.** One of the two signup paths — the Telegram Mini App, the headline distribution channel for a Kyiv lost-pet app — is completely broken for every new user at open beta.

**Fix.** Either add the predicate so the partial index is inferable (`.onConflictDoNothing({ target: schema.users.telegramId, where: isNotNull(schema.users.telegramId) })`), or replace the partial index with an unconditional `UNIQUE (telegram_id)` (NULLs do not collide in Postgres, so the partial predicate buys nothing). Confirm with a one-line repro against a throwaway local Postgres before shipping, in the style of server/src/db/searchResults.ormcheck.ts.

### 4. [P0] Account creation runs in the auth preHandler, which Fastify executes BEFORE any route rate limit — an unauthenticated caller can insert unbounded users/companion_state rows

**Exploit / failure path.** `for i in $(seq 1 200000); do curl -s -H "x-device-id: $(openssl rand -hex 16)" https://shukajpes-api.fly.dev/state & done`. **Impact.** Unbounded growth of `users` and `companion_state` on a single shared-cpu-1x/512MB machine with a 10-connection Postgres pool (server/src/db/index.ts:23). ### 5. [P0] POST /sightings accepts out-of-range lat/lng and permanently overwrites a real lost pet's last-seen coordinate with an off-world value

- **Where:** `server/src/routes/sightings.ts:77` · **Category:** `input-validation-data-loss`

**Evidence.** The ONLY check on lat/lng is `typeof === 'number'`. There is no Number.isFinite, no Kyiv-bbox check, and no [-90,90]/[-180,180] range check — unlike every sibling route (`routes/dogs.ts:311` checks Number.isFinite + KYIV_BBOX; `routes/path.ts:116` checks Number.isFinite + inKyivBbox; `routes/syncMap.ts:160` checks both). The only guard here is `isSyntheticPosition` (sightings.ts:42), which tests one exact coordinate pair. The trust test is the local `haversineM` at sightings.ts:55, which converts degrees to radians and is therefore periodic in 360°. I ran the function's exact source: h(50.4631,30.5174, 50.4631+360, 30.5174) = 1.56e-9 metres, and h(...,30.5174+360) = 9.93e-10 metres — both far inside `dog.radiusM * 2`, so `trusted` is true. `isSyntheticPosition(410.4631, ...)` returns false (verified: Math.abs(410.4501-50.4501)<1e-9 === false). 'sighting' is in CONFIDENT_PLACEMENT_PREFIXES (server/src/services/placementConfidence.ts:60), so the row is not filtered out — it is simply drawn 360° away. The columns are doublePrecision (server/src/db/schema.ts:225-226), so the write succeeds. The identical hole exists on the second write path at server/src/routes/sightings.ts:275 (`POST /sightings/search-result`). Nothing anywhere keeps the previous coordinate, so the original last-seen point is gone.

**Exploit / failure path.** A registered beta user (open beta = anyone can self-register via /auth/register + a verification link) reads the pet ids from the unauthenticated-shaped GET /dogs/nearby, then for each id sends:

POST /sightings
{"dogId":"tg-AbCdEfGhIj","lat":410.4631,"lng":30.5174}

(410.4631 = the pet's real 50.4631 + 360). haversineM returns ~1.6 nanometres, `trusted` is true, the pet is active, so lost_dogs.last_seen_lat becomes 410.4631 and placement_source becomes 'sighting'. The route's limit is 30/min, so one account walks the whole active-pet table in a few minutes. JSON also permits `{"lat":1e999}`, which JSON.parse yields as Infinity (verified in node) — that variant stores Infinity in the column and makes every haversine over the table return NaN for that row.

**Impact.** Irreversible destruction of the single most important field on a real person's lost-pet report: where their animal was last seen. The pet disappears from /dogs/nearby, from /sync/map and from the companion's nearby-pets context (all three filter by distance from the caller), and the owner's original coordinate is not retained anywhere — it cannot be restored by an UPDATE the way `status='expired'` can. Any registered account can do this to every active pet in the table in minutes, with no elevated access and no log line that looks alarming (the request logs as an ordinary accepted sighting).

**Fix.** In both write paths (sightings.ts:77 and sightings.ts:260) replace the `typeof === 'number'` test with the guard the rest of the server already uses: `if (!Number.isFinite(lat) || !Number.isFinite(lng) || !inKyivBbox(lat, lng)) return 400`. `inKyivBbox` is already exported from server/src/lib/servedArea.js and imported by routes/path.ts and routes/syncMap.ts. The bbox check alone kills the 360° wraparound, the Infinity case and the antipodal case in one line.

### 7. [P0] /auth/register is rate-limited per freshly-minted userId, so account creation is unlimited — defeating every per-user rate limit and LLM budget in the service

- **Where:** `server/src/routes/auth.ts:285` · **Category:** `rate-limit-bypass`

**Evidence.** Three facts, each read at HEAD and the third measured. ### 1. [P0] Nothing in the process has a timeout: one slow Postgres query wedges the whole API permanently while /health keeps answering 200

- **Where:** `server/src/db/index.ts:27` · **Category:** `single-point-of-failure`

**Evidence.** I grepped the whole server tree for every timeout knob that could bound a stuck request and found NONE of them: `grep -rn "statement_timeout|idle_timeout|requestTimeout|connectionTimeout|keepAliveTimeout|lock_timeout" server/src server/*.json fly.toml` returns empty. The three ingredients are each confirmed by reading: (1) postgres-js is configured with `connect_timeout: 10` only (db/index.ts:27-31) — that bounds the TCP handshake, not the query, so a query that is accepted and never answered holds its connection out of a pool of 10 (poolMax(), db/index.ts:21-24) forever. (2) Fastify is constructed at server/src/index.ts:63 with only `logger` and `trustProxy: true` — Fastify 5's `requestTimeout` and `connectionTimeout` both default to 0 (disabled), so the socket is never closed either. (3) The liveness probe cannot see it: server/src/index.ts:150 is `app.get('/health', async () => ({ ok: true, ts: new Date().toISOString() }));` — no database, no Redis; and fly.toml:29-34 points the only http_service check at exactly that path. The watchdog does not cover this case either: services/watchdog.ts:34-48 kills the process only when the main thread stops stamping `beat[0]`, i.e. on a SYNCHRONOUS stall; ten connections blocked on async I/O leave the event loop perfectly healthy. The codebase already records the inverse incident in a comment at services/territory.ts:973 — "/territory/leaderboard timed out at 60s and /health, which touches nothing, answered 503 right behind it" — that was a CPU stall, which /health does catch; a pool exhaustion is the case it cannot. Two already-confirmed findings supply the exhaustion: syncMap.ts:213 opens 5-6 pool connections concurrently per request, and ground.ts:298 holds a connection across a worker round-trip.

**Exploit / failure path.** Supabase's pooler has a hiccup, or one unindexed query goes slow under beta load (marksNear reading 2 500 rows per /sync/map, territoryHealth's self-join). Six concurrent /sync/map requests grab 5-6 connections each; the pool of 10 is drained and every subsequent `await db...` queues behind it with no deadline. Because nothing times out, the queue never drains and the connections are never returned. Every real endpoint — /state, /sync/map, /collect/path, /auth/login — hangs open indefinitely; the client has no backoff (confirmed finding at MapView.tsx:1246) so each walker keeps adding 28-40 requests/minute to the pile. Meanwhile `GET /health` returns `{ok:true}` in under a millisecond, so Fly's check passes, the machine is never restarted, no alert fires, and the watchdog stays quiet because the event loop is idle. The beta is down and every automated signal says it is up. Recovery requires a human noticing and restarting by hand.

**Impact.** Total, self-sustaining, silently-healthy outage of the single production machine, triggered by any transient database slowness rather than by an attacker. This is the failure mode that cost eleven hours on 2026-08-05 (watchdog.ts:7) reappearing through the one door the watchdog was not built to cover, and it is the single point of failure most likely to take the whole open beta down.

**Fix.** Three independent bounds, all one line each: (1) add `idle_timeout: 30` and a connection-level `statement_timeout` to the postgres-js options in db/index.ts (postgres-js accepts `connection: { statement_timeout: 15000 }`), so a stuck query releases its connection; (2) set `requestTimeout: 30000` in the Fastify constructor at index.ts:63 (raise it only for the streaming /chat routes, which use the Anthropic SDK's own 10-minute default via services/anthropic.ts:21); (3) point fly.toml's http_service check at a path that actually touches Postgres and Redis — /health/deep already exists at index.ts:152 and returns 503 on failure — or add a second check on it, so a wedged pool becomes a restart instead of a green tick.

### 2. [P1] Every reward-granting UPDATE is a check-then-act across a transaction boundary: concurrent /collect/token or /feed with the same id credits the same paw N times

A grep for a delete against `authTokens` or `authSessions` anywhere in server/src finds none, and neither table appears in any cron (index.ts:291-308 registers decay, scrape, zone-expansion, lost-dog cleanup, spent-item cleanup, metrics snapshot and multiplayer — nothing touches auth). The schema confirms there is no TTL mechanism: db/schema.ts:69-85 has `expiresAt` and `usedAt` columns and only `auth_tokens_user_idx`, plus a UNIQUE on `token_hash` whose index grows with the table. The write is reachable without authentication: `/auth/forgot` (auth.ts:618-630) is in PRE_IDENTITY_AUTH_PATHS (auth.ts:667-675), calls `issueOneTime(user.id, 'reset', RESET_TTL_S)` for any address that has a registered account, and its only limiter is `limitAuth` keyed on `req.ip` (lib/rateLimit.ts:66-68) — which the confirmed P0 at index.ts:93 (`trustProxy: true`) makes attacker-chosen. So the already-confirmed "unmetered mail cannon" at auth.ts:618 is also an unmetered row cannon.

**Exploit / failure path.** Attacker knows one beta tester's e-mail address and POSTs `/auth/forgot {"email":"victim@example.com"}` in a loop, rotating `X-Forwarded-For` so the 10/min IP limit never binds. Each call marks the previous reset token used and inserts a new one. The victim's inbox fills (the already-reported effect) and `auth_tokens` grows without limit — rows that are used, expired, and never collected. The same applies to `/auth/register` resends via the verify path.

**Impact.** Unbounded growth of a table on the credential path, on a 500 MB tier, with a UNIQUE index that every login-adjacent lookup walks. It is slower to fill than collect_events, so it is a P2 rather than a P1 — but it is the same structural gap (no retention anywhere in the auth schema) and it also means a beta's-worth of expired reset hashes is retained indefinitely for no purpose, which is a data-minimisation problem in its own right given there is still no account-deletion path (confirmed P2 at auth.ts:593).

**Fix.** Delete instead of tombstoning where nothing needs the history: in `issueOneTime`, replace the `set({ usedAt })` UPDATE at auth.ts:181-186 with a DELETE of that user's unused tokens of that kind, and add one sweep to a cron (or to the existing spentItemCleanup tick) that removes `auth_tokens` rows past `expires_at` and `auth_sessions` rows past `expires_at` or revoked more than a few days ago.

### 7. [P2] A one-shot retrofit for a bug fixed in PR #158 still reads every companion's memory notes into process memory on every container start

- **Where:** `server/src/services/memoryCleanup.ts:33` · **Category:** `boot-cost`

**Evidence.** The SELECT has no LIMIT and no batching: it pulls the `memory_notes` text of every companion row that has any, into one JS array, and then loops with a sequential UPDATE per row that needs rewriting (memoryCleanup.ts:46-55). It runs at every boot — index.ts:311 `void runMemoryCleanupOnce(app.log)` — and the file's own header (memoryCleanup.ts:1-15) says it is a retrofit for rows "written before PR #158 added the filter to new writes", i.e. its input set is historical and can only shrink to zero, while its cost grows with the table. There is no index it could use: db/schema.ts:131-166 gives `companion_state` only its `user_id` primary key, so the filter is a sequential scan of the whole table plus a TOAST fetch per note. The table grows without bound because the auth preHandler inserts a `users` + `companion_state` row for every unseen device id (confirmed P0 at auth.ts:357 and auth.ts:107), and the machine has 512 MB (fly.toml:38). Boots are frequent by design: CLAUDE.md records that "Pushing to `main` deploys automatically", and spentItemCleanup.ts:111-113 notes the project already discovered "a 24h cron never fires on a service that redeploys several times a day".

**Exploit / failure path.** Open beta runs for a few weeks; `companion_state` reaches tens of thousands of rows, many with a few hundred bytes of memory notes, most of them the free rows the auth hook mints. Every push to main redeploys, and every boot does a full sequential scan of that table and materialises every note in the heap of a 512 MB machine, concurrently with the migration step, the ground-worker warm-up and seven crons all starting at once — for zero rows of actual work, because the bug it retrofits was fixed months ago. Worst case it is an OOM kill at boot, i.e. a crash loop on deploy; ordinary case it is unnecessary latency and connection pressure on the coldest part of the request lifecycle.

**Impact.** Growing, unbounded boot-time memory and database cost, incurred on every deploy, for a migration whose useful life ended with PR #158. It also writes to persisted companion state unattended at boot, which is exactly the kind of data mutation CLAUDE.md asks to be dry-run and read by a human first.

**Fix.** Retire it. The filter it retrofits lives in `maybeUpdateMemory` now, so the historical pass belongs in a one-off script under server/src/db/ (run once, like expire-pet.ts and the other `tsx` scripts in package.json) rather than at index.ts:311. If it must stay at boot for another release, bound it: add `.limit(500)` plus a `memory_notes ~ '^\s*(user|assistant|human|ai)\s*:'` predicate so the scan only touches rows that can possibly match, and delete the call once a boot logs `touched: 0`.

### 8. [P2] Migrations run in the app container at every start with no lock, and the process is not safe to run twice concurrently — a second machine turns a deploy into a crash loop

- **Where:** `server/src/db/migrate.ts:16` · **Category:** `migration-safety`

**Evidence.** I read the whole chain. server/Dockerfile:36 is `CMD ["sh", "-c", "node dist/db/migrate.js && node dist/index.js"]`, so migrations run inside every app container at start, and fly.toml has no `release_command` (I read the file in full — it has `[build]`, `[env]`, `[http_service]`, `[[vm]]` and nothing else), so there is no single-run phase anywhere. migrate.ts (all 24 lines) takes no advisory lock and sets no `lock_timeout`/`statement_timeout`; it just opens `postgres(url, { max: 1 })` and calls the migrator. Drizzle's migrator takes no lock either — I read node_modules/drizzle-orm/postgres-js/migrator.js (4 lines, delegates straight to the dialect) and node_modules/drizzle-orm/pg-core/dialect.js:44-72, which does `select ... order by created_at desc limit 1`, then opens ONE transaction and replays every migration whose `folderMillis` is greater. Two processes doing that simultaneously both read the same watermark and both replay the same DDL. Most of it survives that — I checked all 47 files and they are overwhelmingly `IF NOT EXISTS` — but not all: `server/migrations/0003_pet_species.sql:1` is `ALTER TABLE "lost_dogs" ADD COLUMN "species" text DEFAULT 'dog' NOT NULL;` with no `IF NOT EXISTS`, so a replay from an empty watermark errors, migrate.ts:21-23 does `process.exit(1)`, and the `&&` in the CMD means index.js never starts. The journal itself is clean (I parsed meta/_journal.json: 47 entries, strictly increasing `when`, so no migration is silently skipped by the watermark rule). Separately, the same multi-machine assumption is baked into the runtime: there is no leader election anywhere (`grep -rn "FLY_MACHINE_ID|FLY_ALLOC_ID|leader" server/src` finds only a liveStats label and unrelated leaderboard code), and services/scrape.ts:7 says so in a comment — "single instance, so no leader election. If we scale beyond that, move to a..." — while index.ts:291-308 starts decay, scrape, zone-expansion, two janitors, the metrics snapshot and the 30-bot multiplayer cron unconditionally in every process.

**Exploit / failure path.** Someone runs `fly scale count 2` to survive beta load, or a deploy briefly runs two machines. Both containers start, both run `node dist/db/migrate.js` against the same database, both take the same watermark. One wins the transaction; the other either blocks on its DDL locks with no `lock_timeout` (container sits with no HTTP listener, health check never passes) or errors and exits 1 (`&&` short-circuits, Fly restarts it, it races again — crash loop). If the second machine does come up, both then run every cron: two scrape passes spending Haiku tokens on the same sources, two decay ticks double-draining happiness, and 60 bot walkers instead of 30.

**Impact.** The app is not horizontally scalable, and the failure mode of trying is a crash loop plus double-spent LLM budget and double-applied game decay — i.e. the one lever an operator would reach for under beta load is the lever that breaks production. Also relevant on a single machine: a migration that fails for any reason (the container is where it runs, and it has no timeout) leaves a machine that never opens a port, which the /health check cannot distinguish from a slow boot.

**Fix.** Wrap the migration in a session-level advisory lock and give it a deadline — in migrate.ts, `await sql\`select pg_advisory_lock(hashtext('shukajpes_migrate'))\`` before `migrate(...)` and unlock after, plus `SET lock_timeout = '30s'` and `SET statement_timeout = '5min'` on that connection so a blocked migration fails loudly instead of hanging. Add `IF NOT EXISTS` to 0003_pet_species.sql so a replay is idempotent like the other 46. And before any scale-up, gate the cron block at index.ts:291-308 behind a leader check (a Redis `SET NX` lease, or simply `process.env.FLY_MACHINE_ID === <primary>`), which is the fix services/scrape.ts:7 already anticipates.

### 9. [P3] Boot runs CREATE EXTENSION postgis for an extension nothing in the codebase uses, making every deploy depend on a privilege the app does not need

- **Where:** `server/src/db/migrate.ts:14` · **Category:** `migration-safety`

**Evidence.** This statement runs before the migrator on every container start (Dockerfile:36 chains migrate.js ahead of index.js), and it is the first database statement the container issues. Nothing needs it: `grep -niE "geometry|geography|gist|postgis|earthdistance" server/migrations/*.sql` matches only prose in comments that say the opposite — 0027_territory_ground.sql:16 "bbox columns rather than PostGIS", 0031_territory_reset_10.sql:18 "with no PostGIS it means a hand-rolled..." — and `grep -rn "postgis|ST_" server/src --include=*.ts` returns no code at all (only unrelated CROSSPOST_* env names and a REQUEST_TIMEOUT constant). All proximity in the app is hand-rolled haversine in SQL (e.g. routes/tokens.ts:72-79, routes/walkDestinations.ts:74, services/spawn.ts's `haversineSql`), and the two spatial tables use plain lat/lng bbox indexes (0017_territory_pvp.sql:13, 0027_territory_ground.sql:34). A stale schema comment (db/schema.ts:167 "PostGIS point added via raw SQL migration") is what appears to have motivated the line.

**Exploit / failure path.** The database is moved, restored to a different provider, or its role is narrowed to least privilege — any of which removes the app role's ability to CREATE EXTENSION. `CREATE EXTENSION IF NOT EXISTS postgis` is still not a no-op in that case: it raises a permission error when the extension is absent, migrate.ts:21-23 exits 1, the `&&` stops index.js from starting, and the machine crash-loops on boot. The failure has nothing to do with the app's actual schema, so the log line points at PostGIS while the real cause is a privilege the app never needed.

**Impact.** A gratuitous privilege dependency sitting on the critical boot path of a service that redeploys on every push to main, for a capability zero lines of code use. Low severity because it works today, but it is the kind of latent boot-time coupling that turns a routine database migration or credential rotation into an outage.

**Fix.** Delete migrate.ts:14 and fix the stale comment at db/schema.ts:167 so nobody re-adds it. If PostGIS is genuinely wanted later (it would let the haversine scans in mapData.ts and spawn.ts use a GiST index), install it once by hand as a privileged role and add a real migration that creates the index — not an idempotent-looking statement on every boot.
