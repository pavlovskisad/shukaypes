### 1. [P0] Any Telegram user's account can be taken over by sending `x-device-id: tg:<telegram_id>` — no signature, no invite, no door

- **Where:** `server/src/auth.ts:76`
- **Category:** `auth-bypass`

**Evidence.** Read server/src/auth.ts in full. Mini App accounts are stored with `users.device_id = 'tg:' + telegram_id` (auth.ts:176, restated in the schema comment at server/src/db/schema.ts:19-22 and in wipe-users.ts:130). `device_id` is a plain NOT NULL UNIQUE column (server/src/db/schema.ts:25). The device-id branch of the preHandler looks a row up by exactly that column with no check on the shape of the value beyond 8..128 characters, and `resolveByDeviceId` returns any existing row unconditionally (auth.ts:78-84, comment included). `resolved()` (auth.ts:40-42) sets `registered: doorFor(row) === 'open'`, so a registered+verified victim's row makes `passDoor` (auth.ts:234-239) return immediately. I confirmed via grep across server/src/routes and server/src/services that nothing else re-checks `authVia`, so a `via:'device'` identity is treated identically to a Telegram-signed one everywhere.

**Exploit / failure path.** Attacker learns a victim's Telegram user id (not a secret: it is visible to every bot the person uses, in forwarded-message metadata, and via any of the public "what is my id" bots; this app itself is a Telegram bot ecosystem that crossposts to public lost-pet groups). Attacker sends `curl -H 'x-device-id: tg:123456789' https://<api>/auth/me`. The SELECT on users.device_id matches the victim's row, req.userId becomes the victim's id, the response body is the victim's account (masked e-mail, nickname, pet, telegram flag), and the response header `x-session-token` hands the attacker a 24-hour session slip minted for the victim (auth.ts:359). From there every authenticated route in the app answers as the victim: their tokens, territory, companion chat, presence, /auth/profile, /auth/avatar spend. If the victim is registered but not yet e-mail-verified, POST /auth/register with the attacker's own e-mail and password succeeds — routes/auth.ts:290 only refuses when BOTH registeredAt and emailVerifiedAt are set — converting the hijack into a permanent credentialed takeover of the victim's row. The id space is also enumerable: existing ids answer with a populated account, absent ids mint a fresh one, so the two are distinguishable from the /auth/me body.

**Impact.** Pre-authentication account takeover of every Telegram Mini App user, from a single header, with no rate limit that matters (see the trustProxy and account-flood findings). This invalidates the prior audit's note that "The Telegram path is properly signed and fine" and that device ids are "client-generated random hex (not enumerable)" — for Telegram users the device id IS a public identifier.

**Fix.** Make the synthetic Telegram id un-addressable through the device-id header. In auth.ts:350, reject any presented `x-device-id` matching /^tg:/i before calling resolveByDeviceId (401), and add a check fixture asserting it. Better still, stop overloading `device_id` as the Telegram key: give Telegram rows an opaque random device_id (e.g. `nanoid()`) and rely on the existing `telegram_id` column for identity, so no public value is ever a credential.

### 2. [P0] `trustProxy: true` makes `req.ip` attacker-supplied, so every credential rate limit is a no-op — unlimited password guessing and a trivial scrypt memory-exhaustion DoS on the 512MB machine

- **Where:** `server/src/index.ts:93`
- **Category:** `rate-limit-bypass`

**Evidence.** Read server/src/index.ts:60-147 and server/src/lib/rateLimit.ts in full. `trustProxy: true` in Fastify is passed to proxy-addr as a trust-everything predicate, so `req.ip` resolves to the left-most (furthest, i.e. client-supplied) entry of X-Forwarded-For rather than the hop Fly appended. `limitAuth` is the only limiter on /auth/login, /auth/forgot, /auth/reset, /auth/refresh, /auth/verify and /auth/logout (routes/auth.ts:461, 482, 508, 607, 618, 632), and it keys solely on that value. Cost of one /auth/login: server/src/lib/password.ts:56-63 sets N = 1<<15, R = 8, MAXMEM = 128*N*R*2, and verifyPassword (password.ts:128-137) spends a full derivation even for an unknown address (password.ts:130-132) — 128*32768*8 = 33.5 MB of scrypt working memory and, per the file's own comment at password.ts:42, "tens of milliseconds" on this VM. fly.toml/the brief put this on one shared-cpu-1x with 512 MB.

**Exploit / failure path.** `for i in $(seq 1 100000); do curl -s -H "X-Forwarded-For: 10.$((RANDOM%255)).$((RANDOM%255)).$((RANDOM%255))" -H 'content-type: application/json' -d '{"email":"victim@gmail.com","password":"guess'$i'"}' https://<api>/auth/login; done` — every request lands in a fresh rate-limit bucket, so the 10/min ceiling never fires and the password of any known address can be guessed without limit. Run ~15 of those concurrently instead of serially and each in-flight request holds ~33 MB of scrypt state: the Node process on a 512 MB machine is OOM-killed, taking the whole API down for every real user mid-walk. No credentials and no account are needed for either.

**Impact.** Brute-force protection on every credential endpoint is decorative, and an unauthenticated attacker can knock the single production machine over at essentially zero cost — exactly the 'falls over under beta load' case, except deliberate.

**Fix.** Set `trustProxy: 1` (trust only the one hop Fly appends) instead of `true`, so req.ip is the address Fly observed and cannot be chosen by the caller. Independently, bound concurrent scrypt work: a small semaphore (e.g. 2-4 in-flight derivations, queue the rest) around hashPassword/verifyPassword so memory use is capped regardless of request rate, and add a per-address (not per-IP) failure counter on /auth/login.

### 3. [P0] Every new Telegram Mini App signup 500s: `ON CONFLICT ("telegram_id")` cannot infer the partial unique index

- **Where:** `server/src/auth.ts:191`
- **Category:** `broken-signup`

**Evidence.** Read auth.ts:141-208, server/src/db/schema.ts:23-35 (telegramId is declared with no .unique(), so drizzle creates no constraint of its own), and every migration that mentions telegram_id — grep over server/migrations/*.sql returns only 0010_telegram_auth.sql (the partial index above) and a comment in 0032_invite_codes.sql. I then read the drizzle SQL builder at node_modules/drizzle-orm/pg-core/query-builders/insert.js:104-113: with a `target` and no `where`, it emits `sql`(${targetColumn})${whereSql} do nothing`` where whereSql is undefined — i.e. `on conflict ("telegram_id") do nothing`, with no index_predicate. PostgreSQL's arbiter inference (infer_arbiter_indexes) skips a partial index unless the ON CONFLICT clause carries a WHERE that implies the index predicate, and with no candidate left raises 42P10 'there is no unique or exclusion constraint matching the ON CONFLICT specification'. The sibling device-id insert at auth.ts:107-111 targets `users.deviceId`, which IS a plain UNIQUE column (schema.ts:25), so that path is unaffected — only the Telegram path is. LIMIT: this is a read-only audit with no database, so I could not execute the statement; the conclusion rests on the emitted SQL, the migration text and Postgres's documented inference rule.

**Exploit / failure path.** A new user opens the Mini App. validateInitData passes, resolveByTelegram finds no row with that telegram_id (auth.ts:146-150), and the INSERT at auth.ts:180 runs. Postgres rejects the statement with 42P10. That error is neither InviteRequiredError nor RegistrationRequiredError, so auth.ts:339 rethrows it, the preHandler fails, and index.ts's error handler masks it as a 500. The person sees a broken first screen and can never create an account; retrying produces the same 500 forever. Existing Telegram users are unaffected (they return at auth.ts:151), which is exactly why this would survive testing on the owner's own account.

**Impact.** One of the two signup paths — the Telegram Mini App, the headline distribution channel for a Kyiv lost-pet app — is completely broken for every new user at open beta.

**Fix.** Either add the predicate so the partial index is inferable (`.onConflictDoNothing({ target: schema.users.telegramId, where: isNotNull(schema.users.telegramId) })`), or replace the partial index with an unconditional `UNIQUE (telegram_id)` (NULLs do not collide in Postgres, so the partial predicate buys nothing). Confirm with a one-line repro against a throwaway local Postgres before shipping, in the style of server/src/db/searchResults.ormcheck.ts.

### 4. [P0] Account creation runs in the auth preHandler, which Fastify executes BEFORE any route rate limit — an unauthenticated caller can insert unbounded users/companion_state rows

- **Where:** `server/src/auth.ts:357`
- **Category:** `unauthenticated-write-amplification`

**Evidence.** resolveByDeviceId (auth.ts:65-121) does `db.insert(schema.users)` at auth.ts:107-111 and `db.insert(schema.companionState)` at auth.ts:118 for any `x-device-id` header 8-128 chars long that it has not seen before. The invite gate cannot stop this: server/src/lib/inviteGate.ts:8-11 makes `inviteRequired()` false unless INVITE_REQUIRED is explicitly '1'/'true'/'yes', and it is not set in fly.toml:14-19. The door does not stop it either — `passDoor` at auth.ts:360 throws RegistrationRequiredError and returns 403 only AFTER both inserts have committed. The rate limiter cannot stop it: index.ts:129-148 registers @fastify/rate-limit with `hook: 'preHandler'`, and node_modules/@fastify/rate-limit/index.js:202-209 attaches that handler to `routeOptions[hook]` (a ROUTE-level hook), while node_modules/fastify/lib/route.js:393-394 builds each route's chain as `this[kHooks][hook].concat(opts[hook] || [])` — instance hooks first. The auth plugin's hook is an instance hook (`app.addHook('preHandler', ...)` at auth.ts:245), so it runs, and inserts, before the limiter ever gets a turn.

**Exploit / failure path.** `for i in $(seq 1 200000); do curl -s -H "x-device-id: $(openssl rand -hex 16)" https://shukajpes-api.fly.dev/state & done`. Every request comes back 403 {"error":"registration required"} — and leaves behind one `users` row and one `companion_state` row. Because the limiter runs after the insert, even a 429 response still costs two INSERTs. There is no per-IP ceiling on this path at all.

**Impact.** Unbounded growth of `users` and `companion_state` on a single shared-cpu-1x/512MB machine with a 10-connection Postgres pool (server/src/db/index.ts:23). Every metrics query that scans `users` (services/metrics.ts:127-132, services/accounts.ts:89-110, services/metricsHistory.ts:62) degrades with it, /admin/accounts becomes unusable, and real DAU/retention figures are poisoned by rows that were never people. The 403 response makes it silent — nothing in the logs distinguishes it from beta testers hitting the door.

**Fix.** Move the write out of the un-rate-limited path. Either (a) register an `onRequest` instance hook ahead of the auth hook that applies an IP-keyed ceiling to account CREATION specifically, or (b) do not create the row in the preHandler at all: resolve-only in the hook, return 401/403 for an unknown device id, and mint the row in POST /auth/register, which already carries `limitAuth` (lib/rateLimit.ts:66-68, keyed by req.ip). Option (b) also removes the 'every 404 mints a user' behaviour that the raw-URL fallback at auth.ts:250-252 allows.

### 5. [P0] POST /sightings accepts out-of-range lat/lng and permanently overwrites a real lost pet's last-seen coordinate with an off-world value

- **Where:** `server/src/routes/sightings.ts:77`
- **Category:** `input-validation-data-loss`

**Evidence.** The ONLY check on lat/lng is `typeof === 'number'`. There is no Number.isFinite, no Kyiv-bbox check, and no [-90,90]/[-180,180] range check — unlike every sibling route (`routes/dogs.ts:311` checks Number.isFinite + KYIV_BBOX; `routes/path.ts:116` checks Number.isFinite + inKyivBbox; `routes/syncMap.ts:160` checks both). The trust test is the local `haversineM` at sightings.ts:55, which converts degrees to radians and is therefore periodic in 360°. 'sighting' is in CONFIDENT_PLACEMENT_PREFIXES (server/src/services/placementConfidence.ts:60), so the row is not filtered out — it is simply drawn 360° away. The columns are doublePrecision (server/src/db/schema.ts:225-226), so the write succeeds. The identical hole exists on the second write path at server/src/routes/sightings.ts:275 (`POST /sightings/search-result`). Nothing anywhere keeps the previous coordinate, so the original last-seen point is gone.

**Exploit / failure path.** A registered beta user (open beta = anyone can self-register via /auth/register + a verification link) reads the pet ids from the unauthenticated-shaped GET /dogs/nearby, then for each id sends:

POST /sightings
{"dogId":"tg-AbCdEfGhIj","lat":410.4631,"lng":30.5174}

(410.4631 = the pet's real 50.4631 + 360). haversineM returns ~1.6 nanometres, `trusted` is true, the pet is active, so lost_dogs.last_seen_lat becomes 410.4631 and placement_source becomes 'sighting'. The route's limit is 30/min, so one account walks the whole active-pet table in a few minutes. JSON also permits `{"lat":1e999}`, which JSON.parse yields as Infinity (verified in node) — that variant stores Infinity in the column and makes every haversine over the table return NaN for that row.

**Impact.** Irreversible destruction of the single most important field on a real person's lost-pet report: where their animal was last seen. The pet disappears from /dogs/nearby, from /sync/map and from the companion's nearby-pets context (all three filter by distance from the caller), and the owner's original coordinate is not retained anywhere — it cannot be restored by an UPDATE the way `status='expired'` can. The bbox check alone kills the 360° wraparound, the Infinity case and the antipodal case in one line.
